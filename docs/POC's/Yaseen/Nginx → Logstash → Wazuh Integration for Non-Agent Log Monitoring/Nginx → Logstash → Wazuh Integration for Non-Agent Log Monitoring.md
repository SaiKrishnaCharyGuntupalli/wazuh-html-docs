# Nginx → Logstash → Wazuh Integration for Non-Agent Log Monitoring

## Overview

This implementation demonstrates how logs generated by a non-agent source can be collected, enriched, forwarded, and analyzed within Wazuh without installing a Wazuh agent on the source system.

The objective is to validate a non-agent log collection architecture where Nginx acts as the log source, Logstash performs event collection and metadata enrichment, and Wazuh provides detection, alert generation, and dashboard visibility.

## Phase 1 — Nginx Installation and Configuration

### What is Nginx?

Nginx is a high-performance web server, reverse proxy server, and load balancer. It is widely used to host websites, process HTTP requests, and manage incoming network traffic efficiently. Nginx automatically records client requests and server responses into log files, making it a useful source of operational and security-related information.

### Why is Nginx Used?

Nginx provides detailed access logging that records: client IP address, requested URL, HTTP method, response code, timestamp, and user agent information. These logs can be used for security monitoring, threat detection, and access tracking.

### Why Was Nginx Used in This Implementation?

Nginx was selected as a non-agent log source to simulate a real-world application generating web access events. The objective was to validate whether logs could be collected and monitored in Wazuh without deploying a Wazuh agent on the source system.

### Installation Commands

```bash
sudo apt update
sudo apt install nginx -y
```

### Verify Installation

```bash
sudo systemctl status nginx
```

Expected Output:
```

active (running)

```

## Phase 2 — Nginx Log Generation

### Log Files Used

Nginx generates two primary log files:

**Access Log:**
```

/var/log/nginx/access.log

```
Stores: Successful Requests, Failed Requests, HTTP Methods, URLs Accessed, Response Codes.

**Error Log:**
```

/var/log/nginx/error.log

```
Stores: Application Errors, Server Failures, Runtime Issues.

### Why Generate Logs?

Logs are required to validate the complete ingestion pipeline. To generate test events, multiple requests were intentionally sent to non-existent pages.

Commands:

```bash
curl http://localhost/admin
curl http://localhost/login
curl http://localhost/secret
curl http://localhost/dashboard
curl http://localhost/test123
curl http://localhost/test456
```

These requests generated HTTP 404 responses:
```

GET /test123 HTTP/1.1 404

```
### Verify Log Generation

```bash
tail -f /var/log/nginx/access.log
```

Example Output:
```

127.0.0.1 - - [08/Jun/2026] "GET /test123 HTTP/1.1" 404

```

## Phase 3 — Logstash Deployment

### What is Logstash?

Logstash is a data collection and processing engine within the Elastic ecosystem. It receives data from multiple sources, performs transformation and enrichment, and forwards the processed events to downstream platforms.

### Why is Logstash Used?

Logstash provides: Data Collection, Event Processing, Event Enrichment, Protocol Conversion, and Centralized Log Routing.

### Why Was Logstash Used in This Implementation?

Logstash acts as the intermediary layer between Nginx and Wazuh. It performs: Log Collection, Metadata Enrichment, Event Normalization, and Syslog Forwarding.

---

## Phase 4 — Logstash File Input

```ruby
input {
  file {
    path => "/var/log/nginx/access.log"
    start_position => "beginning"
  }
}
```

### Why File Input?

Nginx stores events in a local log file. The Logstash File Input Plugin continuously monitors the file and reads newly appended log entries.
```

No agent installation is required.

No API integration is required.

No network port exposure is required.

Flow:

Access.log

↓

File Input Plugin

↓

Logstash

```

## Phase 5 — Metadata Enrichment

### What is Metadata Enrichment?

Metadata enrichment is the process of adding additional contextual information to an event before forwarding it to the destination platform.

Enrichment improves: Searchability, Filtering, Multi-Tenant Separation, Dashboard Creation, and Correlation Activities.

### Logstash Configuration

```ruby
filter {
  mutate {
    add_field => {
      "source_platform" => "nginx"
      "event_category"  => "web_access"
      "environment"     => "poc"
      "tenant"          => "nginx_poc"
    }
  }
}
```

### Enriched Fields

| **Field** | **Purpose** |
|---|---|
| `source_platform` | Identifies Nginx as source |
| `event_category` | Identifies web access activity |
| `environment` | Identifies deployment environment |
| `tenant` | Tenant separation and classification |

## Phase 6 — Non-Agent Identification Testing

### Objective

One requirement of multi-tenant environments is the ability to uniquely identify non-agent sources. A custom identifier was introduced to evaluate whether non-agent events could be assigned unique identifiers similar to Wazuh agent identifiers.

### Configuration

```ruby
mutate {
  add_field => {
    "[agent][id]" => "3001"
  }
}
```

### Observation

Within Logstash debug output, the custom identifier was successfully added:

```json
"agent": {
  "id": "3001"
}
```

However, after processing within Wazuh, the dashboard continued displaying:

```json
"agent": {
  "id": "000"
}
```

This indicates that Wazuh internally assigns the manager identifier (`000`) to non-agent syslog events.

## Phase 8 — Logstash Output Configuration

### Purpose

After collecting and enriching Nginx logs, the events must be forwarded to Wazuh for security analysis and alert generation. Two output plugins were configured: File Output Plugin and TCP Output Plugin.

### File Output Plugin

```ruby
output {
  file {
    path  => "/tmp/nginx-events.log"
    codec => rubydebug
  }
}
```

The File Output Plugin was configured for debugging and validation purposes. Before sending logs to Wazuh, it was important to verify that Nginx logs were being collected correctly, metadata enrichment was successful, custom fields were being added, event formatting was correct, and the final event structure matched the expected format.

Verification:

```bash
tail -f /tmp/nginx-events.log
```

Observed Output:

```json
{
  "source_platform": "nginx",
  "event_category": "web_access",
  "tenant": "nginx_poc",
  "custom_agent_id": "3001"
}
```

This confirmed that Logstash enrichment was functioning correctly before forwarding events to Wazuh.

### TCP Output Plugin

```ruby
tcp {
  host => "100.80.13.125"
  port => 1514
  codec => line {
    format => "<134>%{message}"
  }
}
```

The TCP Output Plugin was responsible for forwarding enriched events from Logstash to the Wazuh Manager. TCP was selected because: reliable delivery mechanism, connection-oriented communication, reduced packet loss risk, and suitability for security event transmission.

**Host Configuration:**

```ruby
host => "100.80.13.125"
```

Connected through Tailscale because both the Logstash instance and the Wazuh Manager are on different networks. Tailscale creates a secure peer-to-peer VPN tunnel between them, allowing Logstash to forward Syslog events directly to the Wazuh Manager's private IP over TCP without exposing it to the public internet.

**Port Configuration:**

```ruby
port => 1514
```

Port 1514 is the default Wazuh Syslog ingestion port configured for receiving remote events.

**Message Formatting:**

```ruby
format => "<134>%{message}"
```

The Syslog Priority Header was added to ensure the message follows Syslog formatting standards. This allows Wazuh to correctly identify and process incoming events.

## Phase 9 — Custom Metadata Visibility

### Requirement

A key requirement was to identify non-agent events separately from agent-based events. Since Wazuh automatically assigns `agent.id = 000` for non-agent events, an alternative identification mechanism was required.

### Configuration

```ruby
mutate {
  replace => {
    "message" => "tenant=nginx_poc non_agent_id=3001 %{message}"
  }
}
```

### Why Was This Used?

The objective was to embed tenant and non-agent information directly into the event payload. This ensured the information remained visible after Wazuh processing.

### Example

**Original Log:**
```

127.0.0.1 - - [08/Jun/2026] "GET /test123 HTTP/1.1" 404

```
**Modified Log:**
```

tenant=nginx_poc non_agent_id=3001 127.0.0.1 - - [08/Jun/2026] "GET /test123 HTTP/1.1" 404

```
### Result

The values became visible within: `full_log`, Discover View, Search Queries, and Event Investigation Screens.

This provides a practical method for identifying non-agent events even when Wazuh assigns `agent.id = 000`.

## Phase 10 — Wazuh Syslog Configuration

### Purpose

The Wazuh Manager must be configured to receive logs from external non-agent sources. Without a Syslog listener, Logstash cannot forward events into Wazuh.

Configuration file: `/var/ossec/etc/ossec.conf`

### Syslog Listener Configuration

```xml
<remote>
  <connection>syslog</connection>
  <port>1514</port>
  <protocol>tcp</protocol>
  <allowed-ips>100.80.13.125</allowed-ips>
</remote>
```

### Configuration Explanation

| **Element** | **Value** | **Purpose** |
|---|---|---|
| `connection` | `syslog` | Enables Syslog-based log ingestion |
| `port` | `1514` | Defines the listening port for receiving external logs |
| `protocol` | `tcp` | Configures TCP communication between Logstash and Wazuh |
| `allowed-ips` | `100.80.13.125` | Restricts event ingestion to authorized systems only — improves security and prevents unauthorized log injection |

## Phase 11 — Wazuh Alert Processing

After receiving the event:

1. Wazuh Syslog Listener receives the message.
2. Decoder extracts relevant fields.
3. Rules Engine evaluates the event.
4. Matching rules generate alerts.
5. Alerts are indexed into OpenSearch.
6. Events become searchable within the Wazuh Dashboard.

Example Alert:
```

Rule ID:     31101

Description: Web server 400 error code

Generated From: GET /test123 HTTP/1.1 404

```

![Wazuh Alert Processing](<../../../assets/images/POC's/Yaseen/Nginx → Logstash → Wazuh Integration for Non-Agent Log Monitoring/Phase 11 — Wazuh Alert Processing.png>)

!!! note
    Wazuh does not preserve custom metadata fields added by Logstash, but metadata can be embedded into the log message and successfully carried into Wazuh alerts.
