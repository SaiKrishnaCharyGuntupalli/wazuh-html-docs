    Wazuh Agent Log Buffering and Resynchronization Guide

    1. Objective

    This document explains how Wazuh agents handle log events when the Wazuh Manager is unavailable and how to configure the agent-side buffer on Linux and Windows endpoints.

    The objective is to retain a larger number of events in the Wazuh agent memory buffer during a temporary Wazuh Manager outage and send the queued events after the Manager becomes available again.

    2. Important Behavior During Wazuh Manager Downtime

    Wazuh agents use an in-memory leaky bucket buffer when the Wazuh Manager is unavailable.

    By default, the client-side buffer is configured as follows:

    Queue size: 5000 events
Events per second: 500 events/second

    When the Wazuh Manager goes offline:

    1. The Wazuh agent detects that the Manager is unavailable.
    2. The agent continues attempting to reconnect to the Wazuh Manager.
    3. Events already stored in the agent buffer remain queued.
    4. When the Manager becomes available, the agent sends queued events at the configured rate.in FIFO order
    5. The agent sends events at a throttled rate to avoid flooding the Wazuh Manager.

    The Wazuh agent buffer is stored in memory only.

    This means:

    The agent does not store an unlimited queue of logs on disk.
The agent cannot replay logs that were discarded after the memory buffer became full.
The agent cannot recover events after the Wazuh agent service is restarted while the Manager is unavailable.
The agent cannot recover events after the endpoint is restarted while the Manager is unavailable.

    When the configured queue becomes full, newly generated events can be discarded because the agent cannot keep an unlimited amount of data in memory.

    For long Wazuh Manager outages, increasing the agent buffer can reduce log loss. However, it does not provide unlimited log retention.

    4. Recommended Buffer Configuration

    The following configuration is recommended for a proof of concept or moderate-volume endpoint:

    <client_buffer>
  <disabled>no</disabled>
  <queue_size>100000</queue_size>
  <events_per_second>1000</events_per_second>
</client_buffer>

    Configuration Description

    Parameter Description
    <disabled> Enables or disables the agent-side client buffer
    <queue_size> Maximum number of events stored in the Wazuh agent memory buffer
    <events_per_second> Maximum rate at which queued events are sent to the Wazuh Manager after recovery

    Important Sizing Note

    A larger queue uses more endpoint memory.

    Do not use a very large queue without validating memory usage and expected event volume. The correct queue size depends on:

    Average events per second generated by the endpoint
Expected Wazuh Manager outage duration
Available endpoint memory
Number of agents reconnecting at the same time
Wazuh Manager processing capacity

    Example calculation:

    Average event rate: 10 events per second
Expected outage duration: 2 hours

Required events:
10 × 60 × 60 × 2 = 72,000 events

    For this example, a queue size of 100000 events provides a reasonable buffer.

    Part A — Configure Client Buffer on Linux Wazuh Agent

    Step 1: Connect to the Linux Endpoint

    ssh <username>@<LINUX_AGENT_IP>

    Step 2: Check Wazuh Agent Status

    sudo systemctl status wazuh-agent

    Expected status:

    Active: active (running)

    Step 3: Back Up the Wazuh Agent Configuration

    sudo cp /var/ossec/etc/ossec.conf /var/ossec/etc/ossec.conf.backup

    Step 4: Open the Wazuh Agent Configuration File

    sudo nano /var/ossec/etc/ossec.conf

    Step 5: Add or Update the Client Buffer Configuration

    Inside the <ossec_config> section, add the following configuration.

    <client_buffer>
  <disabled>no</disabled>
  <queue_size>100000</queue_size>
  <events_per_second>1000</events_per_second>
</client_buffer>

    Example placement:

    <ossec_config>

  <client>
    <server>
      <address><WAZUH_MANAGER_IP></address>
      <port>1514</port>
      <protocol>tcp</protocol>
    </server>
  </client>

  <client_buffer>
    <disabled>no</disabled>
    <queue_size>100000</queue_size>
    <events_per_second>1000</events_per_second>
  </client_buffer>

</ossec_config>

    Save the file and exit.

    Step 6: Restart the Wazuh Agent

    sudo systemctl restart wazuh-agent

    Step 7: Verify Wazuh Agent Status

    sudo systemctl status wazuh-agent

    Step 8: Check the Wazuh Agent Log

    sudo tail -f /var/ossec/logs/ossec.log

    Confirm that the agent starts without configuration errors.

    Part B — Configure Client Buffer on Windows Wazuh Agent

    Step 9: Log In to the Windows Endpoint

    Log in to the Windows server using an account with Administrator privileges.

    Step 10: Open Wazuh Agent Configuration File

    Open the following file from powershell  "run as Administrator": it will open in notepad,make changes and enter "ctrl+s"to save

    notepad "C:\Program Files (x86)\ossec-agent\ossec.conf"

    If the Wazuh agent is installed in a different directory, locate the ossec.conf file inside the Wazuh agent installation directory.

    Step 11: Back Up the Wazuh Agent Configuration

    Open Command Prompt as Administrator and run:

    copy "C:\Program Files (x86)\ossec-agent\ossec.conf" "C:\Program Files (x86)\ossec-agent\ossec.conf.backup"

    Step 12: Add or Update the Client Buffer Configuration

    Inside the <ossec_config> section, add the following configuration.

    <client_buffer>
  <disabled>no</disabled>
  <queue_size>100000</queue_size>
  <events_per_second>1000</events_per_second>
</client_buffer>

    Example placement:

    <ossec_config>

  <client>
    <server>
      <address><WAZUH_MANAGER_IP></address>
      <port>1514</port>
      <protocol>tcp</protocol>
    </server>
  </client>

  <client_buffer>
    <disabled>no</disabled>
    <queue_size>100000</queue_size>
    <events_per_second>1000</events_per_second>

    Save the file.

    Step 13: Restart Wazuh Agent Service on Windows

    Open Command Prompt as Administrator and run:

    net stop WazuhSvc
net start WazuhSvc

    Alternatively, use PowerShell as Administrator:

    Restart-Service -Name WazuhSvc

    Step 14: Verify Wazuh Agent Service Status

    Open PowerShell as Administrator and run:

    Get-Service -Name WazuhSvc

    Expected result:

    Status   Name      DisplayName
------   ----      -----------
Running  WazuhSvc  Wazuh

    Step 15: Check Wazuh Agent Logs on Windows

    Open  PowerShell run as administrator:

    Get-Content "C:\Program Files (x86)\ossec-agent\ossec.log" -Tail 50

    Confirm that the Wazuh agent starts without configuration errors.

    Part C — Test Wazuh Manager Outage and Recovery

    Step 16: Confirm Agent Is Connected Before Testing

    On the Wazuh Manager, verify that the agent is active.

    For a Docker-based Wazuh Manager:

    docker exec -it single-node-wazuh.manager-1 /var/ossec/bin/agent_control -l

    For a directly installed Wazuh Manager:

    sudo /var/ossec/bin/agent_control -l

    Confirm that the target agent status is Active.

    Step 17: Stop Wazuh Manager

    If the Wazuh Manager is running in Docker:

    docker stop single-node-wazuh.manager-1

    If the Wazuh Manager is installed directly on the operating system:

    sudo systemctl stop wazuh-manager

    Step 18: Generate Events While the Manager Is Offline

    Linux Test Event

    On the Linux endpoint, run:

    logger "WAZUH_MANAGER_OUTAGE_TEST_LINUX"

    Generate multiple events:

    for i in {1..100}; do logger "WAZUH_MANAGER_OUTAGE_TEST_LINUX_$i"; done

    Windows Test Event

    Open PowerShell as Administrator and run:

    New-EventLog -LogName Application -Source "WazuhTest"

    Generate multiple events:

    Write-EventLog -LogName Application -Source "WazuhTest" -EventId 1001 -EntryType Information -Message "WAZUH_MANAGER_OUTAGE_TEST_WINDOWS"
}

    run the above command multiple times

    Step 19: Check Agent Logs During Manager Downtime

    Linux

    sudo tail -f /var/ossec/logs/ossec.log

    Windows

    Get-Content "C:\Program Files (x86)\ossec-agent\ossec.log" -Wait

    The agent log should show connection attempts or communication errors while the Wazuh Manager is unavailable.

    Step 20: Restore Wazuh Manager

    If the Wazuh Manager is running in Docker:

    docker start single-node-wazuh.manager-1

    If the Wazuh Manager is installed directly on the operating system:

    sudo systemctl start wazuh-manager

    Step 21: Confirm Agent Reconnects

    On the Wazuh Manager, run:

    docker exec -it single-node-wazuh.manager-1 /var/ossec/bin/agent_control -l

    For a directly installed Wazuh Manager:

    sudo /var/ossec/bin/agent_control -l

    Confirm that the agent status changes back to Active.

    Step 22: Verify Queued Events Are Sent

    Linux Agent

    On the Wazuh Manager:

    docker exec -it single-node-wazuh.manager-1 sh -c 'grep -i "WAZUH_MANAGER_OUTAGE_TEST_LINUX" /var/ossec/logs/alerts/alerts.json | tail -n 20'

    Windows Agent

    On the Wazuh Manager:

    docker exec -it single-node-wazuh.manager-1 sh -c 'grep -i "WAZUH_MANAGER_OUTAGE_TEST_WINDOWS" /var/ossec/logs/alerts/alerts.json | tail -n 20'

    If the Wazuh Manager is installed directly on the operating system:

    sudo grep -i "WAZUH_MANAGER_OUTAGE_TEST_LINUX" /var/ossec/logs/alerts/alerts.json | tail -n 20

    sudo grep -i "WAZUH_MANAGER_OUTAGE_TEST_WINDOWS" /var/ossec/logs/alerts/alerts.json | tail -n 20

    Part E — Important Limitations

    1. There Is No Manual Full Resynchronization of Historical Logs

    Wazuh does not provide a command to force an agent to resend all historical local log files after a Wazuh Manager outage.

    The agent forwards events while monitoring files. It does not maintain a permanent disk-based copy of every event for later upload.

    2. The Client Buffer Is Memory-Based

    The client buffer is stored in memory.

    If the Wazuh agent service is restarted during a Manager outage, queued events can be lost.

    If the endpoint is restarted during a Manager outage, queued events can be lost.

    3. Events Can Be Lost When the Queue Is Full

    If the Wazuh Manager outage lasts longer than the configured buffer capacity, the Wazuh agent can discard new events.

    Increasing <queue_size> reduces the chance of loss but does not eliminate it for long outages or high-volume endpoints.

    4. Recovery Rate Must Be Controlled

    After the Wazuh Manager becomes available, many agents can reconnect at the same time.

    A very high <events_per_second> value can overload the Wazuh Manager, Wazuh Indexer, or network.

    Use a controlled value such as:

    <events_per_second>1000</events_per_second>

    Increase this value only after validating Wazuh Manager CPU, memory, queue usage, and Indexer performance.

    Part F — Production Recommendations

    1. Size the <queue_size> value based on expected event rate and maximum acceptable Wazuh Manager outage duration.

    2. Keep the Wazuh Manager highly available where possible.

    3. Monitor Wazuh Manager health, agent connectivity, CPU, memory, disk usage, and queue utilization.

    4. Do not restart Wazuh agents during a Wazuh Manager outage unless necessary, because queued in-memory events can be lost.

    5. Do not restart endpoints during a Wazuh Manager outage unless necessary, because queued in-memory events can be lost.

    6. Use a separate durable log collection architecture, such as Filebeat with Logstash, Kafka, or another disk-backed log shipper, when the requirement is guaranteed delivery during multi-hour or multi-day Wazuh Manager outages.

    7. Test the selected queue size in the actual environment before production rollout.

    8. Use Wazuh client buffer configuration to reduce temporary event loss, but do not treat it as a replacement for durable disk-based log buffering.
