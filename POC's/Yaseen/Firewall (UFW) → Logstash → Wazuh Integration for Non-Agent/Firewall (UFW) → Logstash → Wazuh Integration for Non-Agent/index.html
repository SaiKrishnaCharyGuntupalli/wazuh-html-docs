    Firewall (UFW) → Logstash → Wazuh Integration for Non-Agent Firewall Monitoring

    Objective

    The objective of this implementation is to collect Linux firewall security events generated by UFW (Uncomplicated Firewall), process and enrich those events using Logstash, forward them to the Wazuh Manager, and generate actionable security alerts in the Wazuh Dashboard.

    This implementation demonstrates a complete SOC-style firewall monitoring pipeline where real network security events are collected, analyzed, enriched with custom metadata, and visualized for security monitoring and investigation.

    Architecture Overview

    Phase 1 — UFW Firewall Installation and Configuration

    What is a Firewall?

    A firewall is a security mechanism that monitors and controls incoming and outgoing network traffic based on predefined security rules.

    Think of a firewall as a security guard standing at the entrance of a building. Every network packet entering or leaving the system is checked against configured rules. Based on those rules, traffic can either be allowed or blocked.

    Without a firewall, any device on the network can attempt to communicate with the system. A firewall helps protect servers from unauthorized access, malicious traffic, port scanning activities, and network attacks.

    In this project, the firewall was used as the primary source for generating security events that could be monitored through Logstash and Wazuh.

    What is UFW?

    UFW stands for Uncomplicated Firewall. It is a Linux firewall management utility that provides a simplified interface for configuring firewall rules. Internally, UFW works on top of iptables and helps administrators manage network access without dealing directly with complex firewall commands.

    In enterprise environments, UFW is commonly used to control incoming and outgoing network traffic, protect servers from unauthorized access, and generate security events that can be monitored by SOC teams.

    Why UFW Was Used

    For this project, a reliable source of real security events was required. UFW was selected because every blocked connection attempt automatically generates firewall logs that can be collected and analyzed.

    Using UFW allowed us to simulate a real SOC monitoring use case where network activity, blocked connections, source IPs, destination IPs, and protocols can be monitored and investigated.

    UFW Installation

    Verify the firewall package:

    sudo ufw status

    If UFW is not installed:

    sudo apt update
sudo apt install ufw -y

    Verify installation:

    sudo ufw version

    Enabling Firewall

    sudo ufw enable

    Verification:

    sudo ufw status verbose

    Expected Result: 

    Status: active
    This confirms that the firewall is actively monitoring network traffic.

    Phase 2 — Firewall Rule Configuration

    To generate meaningful security events, multiple deny rules were configured.

    Commands executed:

    sudo ufw deny 3333
sudo ufw deny 4444
sudo ufw deny 5555
sudo ufw deny 6666
sudo ufw deny 7777

    Verification:

    sudo ufw status numbered

    Observed Output: 

    3333  DENY

4444  DENY

5555  DENY

6666  DENY

7777  DENY
    These rules instruct UFW to block traffic attempting to access these ports.

    Phase 3 — Firewall Event Generation

    Initial Testing Approach

    Initially, blocked connections could be generated manually using:

    nc -vz <IP-address> 6666

    This was used only for validation purposes.

    Actual Observation

    While monitoring firewall logs, it was observed that events were continuously being generated even when no manual commands were executed.

    Verification:

    sudo tail -f /var/log/syslog | grep UFW

    Example: 

    [UFW BLOCK] SRC=<IP-address> DST=<IP-address> PROTO=TCP DPT=179

    Why Logs Were Generated Automatically

    The environment already contained real network traffic attempting to connect to the Linux server. Whenever these packets reached the firewall: 

    Network Packet

↓

Linux Kernel

↓

UFW Inspection

↓

Packet Blocked

↓

Syslog Event Generated
    As a result, UFW continuously produced firewall events without requiring manual traffic generation.

    Understanding Port 179

    During analysis, many logs contained DPT=179.

    • DPT = Destination Port
    • 179 = BGP Port (Border Gateway Protocol)

    The project did not configure BGP. The network itself was generating traffic toward port 179, and UFW was automatically logging those blocked connection attempts.

    Phase 4 — Understanding Firewall Logs

    Firewall events are written to: 

    /var/log/syslog
    Monitoring command:

    sudo tail -f /var/log/syslog | grep UFW

    Example: 

    Jun 12 sonarqube kernel: [UFW BLOCK] SRC=<IP-address> DST=<IP-address> PROTO=TCP

    Why "kernel" Appears

    UFW operates inside the Linux networking stack. Whenever network traffic is inspected: 

    Network Packet

↓

Linux Kernel

↓

UFW Processing

↓

Syslog
    Therefore, Linux records the source program as kernel.

    Why "sonarqube" Appears

    The firewall logs were generated on the Sonarqube VM. Linux automatically includes the hostname in log entries. Therefore:

    • sonarqube = Hostname
    • kernel = Process generating event

    Phase 5 — Logstash Deployment

    Why Logstash Was Used

    Logstash acts as a centralized log processing engine. Responsibilities:

    1. Log Collection
    2. Event Parsing
    3. Event Enrichment
    4. Event Routing
    5. Event Forwarding

    With Logstash: 

    Firewall → Logstash → Wazuh
    This provides better scalability and flexibility.

    Phase 6 — Logstash Pipeline Configuration

    Complete Logstash Pipeline

    input {
  file {
    path => "/var/log/syslog"
    start_position => "end"
    sincedb_path => "/dev/null"
    mode => "tail"
  }
}

filter {
  if "UFW BLOCK" in [message] {
    mutate {
      add_field => {
        "source_platform" => "firewall"
        "event_category"  => "network_security"
        "environment"     => "poc"
        "tenant"          => "network_poc"
        "non_agent_id"    => "5001"
        "device_type"     => "linux_ufw"
      }
    }
    mutate {
      replace => {
        "message" => "%{message} tenant=network_poc non_agent_id=5001"
      }
    }
  }
}

output {
  if [source_platform] == "firewall" {
    file {
      path => "/tmp/firewall-events.log"
      codec => rubydebug
    }
    tcp {
      host => "100.80.13.125"
      port => 1514
      codec => line {
        format => "<134>%{message}"
      }
    }
  }
}

    Phase 6.1 — Input Section

    Purpose

    The Input section is responsible for collecting firewall logs from the Linux operating system. UFW firewall events are written to /var/log/syslog, therefore Logstash was configured to continuously monitor this file.

    File Input Configuration

    input {
  file {
    path => "/var/log/syslog"
    start_position => "end"
    sincedb_path => "/dev/null"
    mode => "tail"
  }
}

    Explanation of Each Parameter

    path

    path => "/var/log/syslog"

    Specifies the file Logstash should monitor. UFW firewall events are written into syslog. Without monitoring syslog, Logstash cannot collect firewall events.

    start_position

    start_position => "end"

    Tells Logstash where to begin reading. Options are beginning or end. Only newly generated firewall events were required — old historical logs were not needed. Therefore: read new logs only.

    sincedb_path

    sincedb_path => "/dev/null"

    Controls Logstash file tracking. Normally Logstash remembers the last read position inside a sincedb file. For testing, Logstash was set to always read events fresh, so tracking was disabled.

    mode

    mode => "tail"

    Continuously monitors file updates. Firewall events are generated continuously so Logstash must keep watching the file in real time.

    Result: Logstash successfully collected firewall events from Linux syslog.

    Phase 6.2 — Filter Section

    Purpose

    The filter section was used to identify firewall events and enrich them with custom metadata.

    Without filtering: Raw Firewall Logs

    With filtering: Enriched Security Events

    Firewall Event Detection

    if "UFW BLOCK" in [message]

    Purpose: Process only firewall block events. Syslog contains many types of logs (SSH logs, system logs, kernel logs, application logs, firewall logs). Only UFW BLOCK events were required.

    Phase 6.3 — Metadata Enrichment

    SOC analysts often need additional context. Metadata helps identify event source, environment, tenant, device type, and non-agent source.

    Field Value Purpose
    source_platform firewall Identifies firewall as the source
    event_category network_security Classifies event type
    environment poc Identifies testing environment
    tenant network_poc Logical tenant separation
    non_agent_id 5001 Unique identifier for non-agent source
    device_type linux_ufw Identifies Linux UFW firewall source

    Result: Firewall events now contain meaningful SOC metadata.

    Phase 6.4 — Message Modification

    mutate {
  replace => {
    "message" => "%{message} tenant=network_poc non_agent_id=5001"
  }
}

    Why Was This Added?

    During testing, Wazuh was receiving events but some custom fields were not visible after processing. To preserve important identifiers, metadata was appended directly into the message payload.

    Before: 

    [UFW BLOCK] SRC=<IP-address> DST=<IP-address>
    After: 
    [UFW BLOCK] SRC=<IP-address> DST=<IP-address> tenant=network_poc non_agent_id=5001
    Result: Custom identifiers remained visible after forwarding to Wazuh.

    Phase 6.5 — File Output Validation

    Before sending logs to Wazuh, validation was required. Therefore a temporary file output was configured.

    file {
  path => "/tmp/firewall-events.log"
  codec => rubydebug
}

    Why rubydebug?

    codec => rubydebug displays the complete event structure. Used to verify metadata fields, parsed values, and event formatting.

    Verification

    tail -f /tmp/firewall-events.log

    Observation

    Successfully observed: source_platform, tenant, device_type, event_category, non_agent_id.

    Result: Logstash enrichment validated successfully.

    Phase 6.6 — TCP Output to Wazuh

    Forward enriched firewall events to Wazuh Manager:

    tcp {
  host => "100.80.13.125"
  port => 1514
  codec => line {
    format => "<134>%{message}"
  }
}
    Parameter Value Purpose
    host 100.80.13.125 Destination Wazuh Manager IP
    port 1514 Wazuh Syslog Listener Port
    codec line Send events as single-line syslog messages
    format <134>%{message} Convert firewall event into syslog format expected by Wazuh

    Result: Firewall events successfully forwarded to Wazuh Manager.

    Phase 7 — Wazuh Manager Configuration

    After Logstash successfully collected and enriched firewall events, the next step was to configure the Wazuh Manager to receive those events. The Wazuh Manager acts as the central security analysis engine. It receives incoming logs, processes them using decoders and rules, and generates alerts that can be viewed in the Wazuh Dashboard.

    Wazuh Syslog Listener Configuration

    The Wazuh Manager was configured to receive Syslog events on TCP port 1514. 

    Configuration file: /var/ossec/etc/ossec.conf
    Purpose: Allow external systems such as Logstash to forward events into Wazuh.

    Verifying Incoming Events

    After Logstash started forwarding logs, verification was performed using:

    docker exec -it single-node-wazuh.manager-1 bash

    Inside the container:

    tail -f /var/ossec/logs/archives/archives.json

    What is archives.json?

    archives.json stores raw events received by Wazuh before alert generation. Purpose:

    1. Verify logs are reaching Wazuh
    2. Verify log content
    3. Troubleshoot decoder issues
    4. Validate event reception

    Observation

    Firewall events appeared in archives.json:

    {
  "source_platform": "firewall",
  "tenant": "network_poc",
  "event_category": "network_security"
}

    This confirmed the following communication was successful: 

    Firewall

↓

Logstash

↓

Wazuh Manager

    Phase 8 — Wazuh Rule Development

    Problem Identified

    Events were visible in archives.json but no alerts were appearing in alerts.json. 

    archives.json  → YES

alerts.json    → NO

Dashboard      → NO
    This indicated that Wazuh was receiving logs but not generating alerts.

    Understanding Wazuh Alert Processing

    Wazuh generates alerts only when: 

    Raw Event

↓

Decoder Match

↓

Rule Match

↓

Alert Generated

If decoder fails:

archives.json = YES

alerts.json   = NO

If rule fails:

archives.json = YES

alerts.json   = NO

    Local Rule Creation

    Custom rule file: /var/ossec/etc/rules/local_rules.xml

    <group name="firewall,">
  <rule id="100010" level="7">
    <if_sid>4100</if_sid>
    <match>UFW BLOCK</match>
    <description>UFW Firewall Blocked Connection</description>
    <group>firewall,ufw,network_security,</group>
  </rule>
</group>

    Rule Explanation

    Element Value Purpose
    id 100010 Unique identifier for custom firewall alert
    level 7 Alert severity — higher level = higher importance
    if_sid 4100 Trigger only after Wazuh's built-in firewall rule matches — prevents false positives
    match UFW BLOCK Detect UFW firewall block events

    Rule Validation

    /var/ossec/bin/wazuh-logtest

    Sample input: 

    Jun 12 sonarqube kernel: [UFW BLOCK] SRC=<IP-address> DST=<IP-address> PROTO=TCP
    Result: 
    Rule ID:     100010

Description: UFW Firewall Blocked Connection

Level:       7

Alert Generated: YES
    This confirmed the rule was working correctly.

    Phase 9 — Troubleshooting and Issue Resolution

    Issue 1 — Logstash Unable to Read Syslog

    Error: Permission denied /var/log/syslog

    Root Cause: Logstash user was not a member of the ADM group.

    Verification:

    ls -l /var/log/syslog

    Output: 

    -rw-r----- syslog adm
    Solution:

    sudo usermod -aG adm logstash
sudo systemctl restart logstash

    Result: Logstash successfully read syslog.

    Issue 2 — Events Not Appearing in Wazuh

    Observation: 

    syslog   → YES

logstash → YES

wazuh    → NO
    Investigation: Verified with tail -f /tmp/firewall-events.log — confirmed Logstash processing. Forwarding issue identified and corrected.

    Issue 3 — Logs in archives.json but No Alerts

    Observation: 

    archives.json = YES

alerts.json   = NO
    Root Cause: Custom rule not matching.

    Solution: Created Rule 100010.

    Result: Alert generation successful.

    Issue 4 — local_rules.xml Permission Denied

    Error: Could not open local_rules.xml — Permission denied

    Verification:

    ls -l local_rules.xml

    Observed: Incorrect ownership.

    Solution:

    chown wazuh:wazuh /var/ossec/etc/rules/local_rules.xml

    Result: Rule file loaded successfully.

    Issue 5 — Rule Validation Failure

    Investigation:

    /var/ossec/bin/wazuh-logtest

    Observation: Only Rule 4100 fired. Custom rule not firing.

    Root Cause: Rule loading issue.

    Solution: Fixed permissions and restarted Wazuh.

    Result: Rule 100010 successfully triggered.
